# sns-timeline

X（旧Twitter）風のテキストタイムライン型SNS（プログラミングスクールの学習用課題）。

ログインした複数のユーザーが、テキストや画像を投稿し、お互いの投稿にいいね・コメントできるシンプルなSNS。フォローしたユーザーの投稿がタイムラインに新しい順で並ぶ。X/Twitterとの違いとして、**インプレッション数（表示回数）を表示しない**、**リツイート（リポスト）機能を持たない**ことで、数字や拡散を気にせず投稿できる場を目指す。

フェーズ1（ローカル環境）の機能はすべて実装済みで、認証・投稿・画像の添付・タイムライン・いいね・コメント・フォロー・ユーザー検索・プロフィール（アイコン画像の変更を含む）が動く。次はフェーズ2（AWSへのデプロイ）（[開発フェーズ](#開発フェーズ)参照）。画面と操作は、HTML/CSS/JavaScriptだけで作った[プロトタイプ（mock/）](#mock-について)で先に確認できる。

## 開発の背景・目的

プログラミングスクールの課題として、要件定義 → 設計 → 実装 → AWSへのデプロイまでを一通り作り切ることを目的とした学習用アプリ。前回の課題（Trello風タスク管理アプリ）は「1人で使う」アプリだったが、今回は「ログインした複数のユーザーが、お互いの投稿にいいね・コメントする」アプリにすることで、次のような複数人利用ならではの設計を学ぶ。

| 学ぶこと | このアプリのどこで使うか |
|---|---|
| 認証・認可（ログイン、本人だけが操作できる制御） | ログイン機能、投稿・コメントの削除 |
| 多対多のデータ設計 | いいね（ユーザー×投稿）、フォロー（ユーザー×ユーザー） |
| 集計クエリとN+1問題 | いいね数・コメント数の表示 |
| ページング | タイムラインの無限スクロール |
| ファイルアップロードとクラウドストレージ | 画像投稿（Amazon S3） |
| AWSでの本番に近い構成 | EC2 + ALB + RDS + S3、Terraform |

詳しくは [要件定義書 1. 背景・目的](./要件定義書.md#1-背景目的) を参照。

### X/Twitter との違い

| X/Twitter | このアプリ | 理由 |
|---|---|---|
| インプレッション数を表示する | **表示しない** | 「何人に見られたか」を気にせず、気軽に投稿できる場にするため |
| リツイート（リポスト）・引用ができる | **機能を用意しない** | 拡散よりも、投稿そのものへの反応（いいね・コメント）を大事にするため |

## 主な機能

- **ログイン機能**：ユーザー名・表示名・メールアドレス・パスワードで新規登録し、メールアドレスとパスワードでログイン。ログインしていないと他の画面は使えない
- **投稿**：140文字以内のテキストを投稿。自分の投稿だけを編集（「編集済み」と表示）・削除（確認ダイアログあり）できる
- **画像投稿**：1つの投稿に最大4枚（jpg/png/gif/webp、1枚5MBまで）。枚数に応じたグリッドで表示
- **タイムライン**：フォローしているユーザーと自分の投稿を新しい順に20件ずつ表示し、スクロールで続きを読み込む。他の人の新しい投稿は15秒ごとに確認し、一番上を見ているときはそのまま、読んでいる途中は「新しい投稿 N件」ボタンで知らせる
- **いいね**：投稿へのいいね・取り消し。第三者を含むいいね数と、自分がいいね済みかを表示
- **コメント**：投稿へのコメント（返信は不可）。第三者を含むコメント数を表示し、自分のコメントだけ削除できる
- **フォロー**：他のユーザーのフォロー・解除。フォロー数・フォロワー数とその一覧を表示
- **ユーザー検索**：ユーザー名（@ID）・表示名でユーザーを検索。投稿者・コメント者の名前からもプロフィールへ移動してフォローできる
- **プロフィール**：ユーザーごとの情報と投稿一覧。自分の表示名・自己紹介・アイコンを編集できる

機能IDごとの一覧は [機能一覧](./機能一覧.md)、権限（誰が何をできるか）は [機能一覧 権限のまとめ](./機能一覧.md#権限のまとめ誰が何をできるか) を参照。

## mock/ について

`mock/index.html` をブラウザで直接開く（ダブルクリックでよい。サーバーやインストールは不要）と確認できる、HTML/CSS/JavaScriptだけで作った画面確認用のプロトタイプ。React・Spring Bootで実装する前に、要件定義書・機能定義書で決めた画面遷移・入力チェック・ボタンの状態に抜けや違和感がないかを触って確かめるためのもので、実装の本体ではない。

| ファイル | 役割 |
|---|---|
| `mock/index.html` | 画面の土台。デモ用バー（ユーザー切替・データ初期化）を含む |
| `mock/style.css` | 見た目。ダークモード・スマホ幅（375px〜）にも対応 |
| `mock/script.js` | 画面の切り替え（URLの `#/...`）、サンプルデータ、全機能の処理 |

### 使い方

1. `mock/index.html` を Google Chrome で開く
2. ログイン画面の「デモ用アカウント」をクリックしてログインする（パスワードはすべて `password123`）。花子（`hanako@example.com`）はフォロー中が多く、タイムラインの追加読み込みまで確認できる
3. 画面上部の「ユーザー切替」で別のユーザーに切り替えると、第三者からのいいね・コメント・フォローを確認できる
4. 「データを初期化」で、投稿・いいね・コメント・フォロー・登録したユーザーを最初の状態に戻せる

### 本番の実装との違い

- データはブラウザの localStorage にだけ保存される。別のブラウザ・別のPCとは共有されない
- パスワードはハッシュ化せずに保存している。本人チェックもブラウザ内で行っているだけで、本番ではすべてサーバー側（Spring Boot）で行う（[認証機能](./機能定義書/認証機能.md)）
- 画像は localStorage に保存するため、大きな画像をたくさん投稿すると保存容量（5MB程度）を超え、再読み込みで消えることがある。本番ではS3に保存する（[画像投稿機能](./機能定義書/画像投稿機能.md)）
- いいね・フォローの通信失敗時の巻き戻し（楽観的更新の失敗）は、通信が無いため再現していない

## ローカルでの動かし方

### 必要なもの

- Node.js（フロントエンド）
- JDK 21（[Eclipse Temurin](https://adoptium.net/) など）
- Docker Desktop（PostgreSQLをコンテナで動かすため）

### 初回のみ：設定ファイルの作成

秘密情報を含む設定ファイルはGitに含めていないため、雛形（`.example`）をコピーして作る。

| 作るファイル | コピー元 | 書き換える値 |
|---|---|---|
| `backend/.env` | `backend/.env.example` | `POSTGRES_PASSWORD`（ローカルDBのパスワード） |
| `backend/src/main/resources/application-local.properties` | 同じ場所の `.example` | `spring.datasource.password`（上と同じ値）、`app.jwt.secret`（32バイト以上のランダムな文字列） |
| `frontend/.env` | `frontend/.env.example` | そのままでよい（`VITE_API_BASE_URL=http://localhost:8080`） |

### backend/ の動かし方

```bash
cd backend
docker compose up -d                                       # PostgreSQLコンテナを起動
./gradlew.bat bootRun --args='--spring.profiles.active=local'   # Windows
# ./gradlew bootRun --args='--spring.profiles.active=local'     # Mac/Linux
```

`http://localhost:8080/api/health` にアクセスして `{"status":"UP"}` が返ってくれば起動成功。DBの接続情報・JWTの署名キーは `backend/src/main/resources/application-local.properties`（Gitには含めない）に記載する。

> **compose のプロジェクト名は `sns-timeline` に固定している**（`docker-compose.yml` の `name:`）。省略するとフォルダ名の `backend` になり、同じPCで `backend/` フォルダの compose を使う別プロジェクトとサービス名（`postgres`）が同じだと、相手のコンテナを置き換えてしまうため。
>
> 2026-11 より前に `docker compose up -d` したことがある場合は、古いプロジェクト名（`backend`）のコンテナが残っているので、一度だけ `docker rm -f sns-timeline-postgres` してから `docker compose up -d` し直す。データの保存先（ボリューム）も `backend_postgres-data` から `sns-timeline_postgres-data` に変わるため、DBは空の状態から始まる（古いデータが不要なら `docker volume rm backend_postgres-data` で削除できる）。

### frontend/ の動かし方

```bash
cd frontend
npm install
npm run dev
```

`http://localhost:5173` をブラウザ（Google Chrome推奨）で開き、ログイン画面が表示されれば起動成功。「新規登録」からアカウントを作ると、タイムライン（ホーム）が表示され、「投稿する」から投稿できる。

その他のコマンド（バックエンドのテストは `cd backend && ./gradlew.bat test`。テスト用のPostgreSQLを起動するため Docker を起動しておく。[設計書 7章](./設計書.md#7-テスト方針)）：

```bash
npm test          # 単体テスト・コンポーネントテスト（Vitest）
npm run test:watch  # ファイルを保存するたびにテストを実行
npm run build     # 本番用ビルド
npm run preview   # ビルド結果のプレビュー
npm run lint      # oxlintによる静的解析
npm run gen:api-types  # API仕様書からAPIの型（src/api/schema.d.ts）を生成
npm run build:api-doc  # API仕様書を1枚もののHTML（docs/api/dist/index.html）にする
```

APIを変更したら、`backend/` で `./gradlew.bat test -PupdateApiDoc`（API仕様書の更新）、`frontend/` で `npm run gen:api-types`（型の更新）を実行し、生成されたファイルも一緒にコミットする（忘れると CI が失敗する。[設計書 4-4](./設計書.md#4-4-api仕様書openapiの自動生成)）。

> 2026-11 より前に `application-local.properties` を作った場合は、Swagger UI を使うために `application-local.properties.example` の末尾の `springdoc.*` の2行を追記する。

> フロントエンド・バックエンドを同時に動かす場合は、ポートを変更しないこと。バックエンドは`8080`固定、フロントエンドは`5173`固定でないとCORSエラーになる（詳細は [CLAUDE.md](./CLAUDE.md#5-開発サーバー起動時のポート管理) 参照）。Claude Codeに「開発サーバーを起動して」と頼むと、`.claude/skills/dev-servers` のルールに従って起動する。

### 動作確認のコツ

複数ユーザーの機能（いいね数・コメント数・フォロー）を確認するには、ブラウザの通常ウィンドウとシークレットウィンドウで**別々のユーザーとしてログイン**するとよい（JWTはlocalStorageに保存されるため、ウィンドウごとに別のユーザーでログインできる）。

## AWS構成（フェーズ2）

```
ブラウザ ──HTTP──▶ ALB ──▶ EC2（Nginx ＋ Spring Boot） ──▶ RDS（PostgreSQL）
                                    │
                                    └──▶ S3（画像）◀── ブラウザ（署名付きURLで表示）
```

- VPCを自分で設計し、ALBは2つのAZ、RDSはプライベートサブネットに置く
- EC2はパブリックサブネットに置き、セキュリティグループでALBからの通信だけを許可する（NAT Gatewayを使わず無料利用枠に収めるため）
- EC2からS3へは、アクセスキーではなくIAMロールでアクセスする

構成図・セキュリティグループ・コストの詳細は [インフラ構成図](./インフラ構成図.md) を参照。**ALBはAWSアカウントの作成時期によっては無料利用枠の対象外**になるため、構築前に必ず確認すること。

## 開発の進め方（GitHub運用）

- `main` ブランチへの直接pushは禁止（ブランチ保護設定済み）。作業ブランチを作り、Pull Request経由でマージする
- 作業前にIssueを作成し、ブランチ名は `種別/Issue番号-説明`（例：`feature/12-add-login-form`）
- PRがマージされると、作業ブランチは自動で削除される
- 実装を変えたら、同じPRで対応するドキュメントも更新する

詳しいルールは [CLAUDE.md](./CLAUDE.md) を参照。

## 品質チェック

実装がある程度進んだら、[品質チェックリスト](./品質チェックリスト.md) に沿ってフロントエンド・バックエンド・ドキュメント整合性をチェックし、結果を [品質チェック記録](./品質チェック記録.md) に追記する。Claude Codeに「品質チェックして」と頼むと、`.claude/skills/quality-review` の手順でチェックする。

## 対象外の機能

リツイート（リポスト）・引用、インプレッション数、コメントへの返信、ダイレクトメッセージ、通知、投稿の検索・ハッシュタグ、ブロック・ミュート・通報、おすすめタイムライン、スマホアプリ化は今回のスコープ外。詳細は [要件定義書 4. 対象外](./要件定義書.md#4-対象外今回は絶対に作らないもの) を参照。
