## 第1章: 認証・認可とセキュリティ(8問)

### Q1. セッション認証とトークン認証

> 「セッション認証」と「トークン(JWT)認証」の違いを説明してください。
> また、このアプリでJWTを採用した理由(利点)も述べてください。

**回答:**

#### セッション認証との違い

- **セッション認証(ステートフル):** サーバーのメモリや共有セッションストア(Redis等)にログイン状態(セッション情報)を保持し、クライアントにはSession IDのみをCookie等で渡して照合します。
- **トークン/JWT認証(ステートレス):** ユーザーIDや権限情報を電子署名付きのトークン自体に埋め込んでクライアントへ渡します。サーバー側はセッション状態を保持せず、リクエストごとに送られてくるトークンの電子署名を秘密鍵で検証するだけで本人確認を行います。

#### Sns TimeLineでJWTを採用した利点

- **ステートレス性による高いスケーラビリティ:** サーバー側でセッション管理用のDB/Redisが不要なため、バックエンドのコンテナ(ECS/Fargateなど)をAuto Scalingで手軽に増減できること。
- **フロントエンド(SPA)との親和性:** APIサーバーと静的ホスティング環境(S3+CloudFront)がドメインや物理サーバーをまたぐ構成でも、HTTPヘッダー(`Authorization: Bearer <token>`)経由で柔軟に通信を完結できること。

> **※このアプリの実際の構成:** 現在のAWS構成案は ECS/Fargate や S3+CloudFront ではなく、EC2 1台の中で Nginx(Reactのビルド済みファイルを配信)と Spring Boot を Docker Compose で動かす構成です([インフラ構成図.md](../インフラ構成図.md))。ただしJWTでステートレスにしているため、将来EC2を複数台に増やしてもセッション共有の仕組みを追加せずに済む、という利点はこの構成でも当てはまります。

### Q2. アクセストークンとリフレッシュトークン

> 以下について説明してください:
> - なぜトークンを2種類に分けるのか
> - アクセストークンの有効期限が短い理由
>
> (アクセストークン: 15分 / リフレッシュトークン: 7日)

**回答:**

#### 2種類に分ける理由

セキュリティと利便性(UX)の両立のためです。1つの長寿命トークンを常時通信に使うと、通信傍受やXSS等で漏洩した際の被害が計り知れない。短命なアクセストークンと、更新専用の安全に隔離されたリフレッシュトークンに責務を分けることでリスクを局所化します。

#### アクセストークンの有効期限が短い理由(15分)

万が一アクセストークンが第三者に奪取された場合でも、不正利用できるウィンドウ(猶予時間)を最大15分間に限定するためです。JWTはステートレスゆえに「発行後にサーバー側から即時失効させる」ことが原則困難なため、有効期限自体を極力短く設定しておく必要があります。

> **※このアプリの実際の構成:** このアプリではリフレッシュトークンは導入しておらず、JWTは1種類のみで有効期限は24時間です(`app.jwt.expiration=24h`)。期限が切れると再ログインが必要になります。上記の理由から、本番運用するならアクセストークンを短命にしてリフレッシュトークンを導入するのが改善点だと考えています。

### Q3. パスワードのハッシュ化

> 「ハッシュ化」と「暗号化」の違いを説明してください。
> また、なぜパスワード保存にハッシュ化を使うのか述べてください。

**回答:**

#### ハッシュ化と暗号化の違い

- **暗号化(可逆):** 鍵(暗号鍵・復号鍵)を用いてデータを暗号文に変換し、復号鍵を使えば元の平文に戻すことができます。
- **ハッシュ化(不可逆):** 一方向性の計算アルゴリズムを用い、不可逆な固定長の文字列に変換します。元の平文に戻す(復号する)ことは数学的に不可能です。

#### なぜパスワード保存にハッシュ化を使うのか

万が一データベースが不正アクセス等で外部に流出した場合でも、不可逆なハッシュ値(かつソルト+ストレッチングを施したBCrypt/Argon2等)であれば、攻撃者はおろかシステム管理者であってもユーザーの生パスワードを特定できないようにするためです。

### Q4. 認可(Authorization)

> 「認証」と「認可」の違いを説明し、
> 「自分の投稿のみ編集・削除できる」機能がどちらに該当するか答えてください。

**回答:**

#### 認証と認可の違い

- **認証(Authentication):** 「あなたは誰か?」を確認・特定すること(例:ID・パスワードで本人確認を行いログインすること)。
- **認可(Authorization):** 「特定されたあなたに、その操作を行う権限があるか?」を判定・許可すること(例:一般ユーザーは管理画面に入れない、他人のデータは消せない等)。

#### 「自分の投稿のみ編集・削除できる」機能の該当分類

「**認可**」に該当します(ログイン済みのユーザー自身と、編集対象の投稿の所有者IDが一致しているかを検証して操作を許可する処理)。

### Q5. CORS設定の実務理解

> 以下について説明してください:
> - 本番環境でのCORS設定の変更点
> - `allowedOrigins("*")` の問題点

**回答:**

#### 本番環境でのCORS設定の変更点

開発環境ではローカルホスト(`http://localhost:3000` や `5173` 等)を許可しますが、本番環境では本番フロントエンドの正規ドメイン(例:`https://raisetimeline.example.com`)のみを厳密にホワイトリスト指定します。

#### `allowedOrigins("*")` の問題点

悪意ある第三者が作成したフィッシングサイトや攻撃用Webページから、ユーザーのブラウザを介して自社APIを自由に叩くクロスオリジンリクエストが許可されてしまい、CSRF攻撃や機密情報の不正取得につながる重大な脆弱性となります。

### Q6. SQLインジェクション

> SQLインジェクションとは何か説明してください。
> また、MyBatisで防ぐための実装上の注意点を述べてください。

**回答:**

#### SQLインジェクションとは

ユーザー入力値(フォームやURL引数)にSQL文の一部となる特殊記号を紛れ込ませ、開発者が意図しない不正なSQLを実行させてデータベースの改ざんや情報漏洩を引き起こす攻撃手法です。

#### MyBatisでの防止策・注意点

- 必ずプレースホルダー記法(バインド変数)である `#{param}` を使用します(内部的にPreparedStatementが使われ、入力値が自動で安全にエスケープされます)。
- 文字列置換を行う `${param}` は原則使用禁止とします(テーブル名やソート順を動的に指定する等の例外を除き、`${}` に入力値を直接埋め込むとSQLインジェクションが発生します)。

> **※このアプリの実際の構成:** このアプリはMyBatisではなく Spring Data JPA を使っています。メソッド名からのクエリ自動生成か、`@Query` の名前付きパラメータ(`:followerId` など)によるバインドを使っており、SQL文字列に入力値を連結していないため、MyBatisの `#{}` と同じ考え方でSQLインジェクションを防いでいます。

### Q7. XSS(クロスサイトスクリプティング)

> 以下について説明してください:
> - `<script>alert('攻撃')</script>` が投稿された場合のリスク
> - Reactでの対策方法

**回答:**

#### `<script>alert('攻撃')</script>` が投稿された場合のリスク

他のユーザーがそのタイムラインを閲覧した際、ブラウザ上で攻撃者が仕込んだ悪意あるJavaScriptが自動実行されます。これにより、localStorageに保管されたアクセストークンの窃取、不正なセッションハイジャック、意図しない投稿・いいねの強制実行などが引き起こされます。

#### Reactでの対策方法

ReactはJSX内の変数展開(`{post.content}`)時に、デフォルトでHTML特殊文字(`<`, `>`, `&`, `"`, `'`)を自動エスケープ(サニタイズ)するため、通常の記述をしていればスクリプトとして実行されず単なる文字列として描画されます。

**注意点:** `dangerouslySetInnerHTML` を使用するとこの自動エスケープが無効化されるため、ユーザー入力値に対しては絶対に使用しないことが対策となります。

### Q8. HTTPSと本番セキュリティ

> 以下について説明してください:
> - ALBを使った場合のSSL/TLS証明書の配置場所
> - ALB〜バックエンド間通信のHTTPS必要性

**回答:**

#### ALBを使った場合のSSL/TLS証明書の配置場所

**ALB(Application Load Balancer)** に配置します(AWS Certificate Manager [ACM] で発行・管理した証明書をALBのHTTPSリスナーにアタッチします)。

#### ALB〜バックエンド間通信のHTTPS必要性

ALBでSSL終端(SSL Termination)を行い、内部のVPC(プライベートサブネット)内のECS/EC2への転送はHTTPで行う構成が実務上一般的です。プライベートネットワーク内は外部から隔離されており、証明書管理コストの削減とサーバーの暗号化負荷軽減が図れるためです(※金融システム等、極めて機密性の高い要件ではEnd-to-End暗号化のため内部もHTTPS化するケースがあります)。

> **※このアプリの実際の構成:** 現在の構成案では、無料枠に収めるため(NAT Gatewayが有料のため)EC2をパブリックサブネットに置き、セキュリティグループでALBからの通信だけを許可しています。また、独自ドメインを取得していないためHTTPS(ACM)はまだ使っておらずHTTPのみです。JWTを平文のHTTPで送るのは本来危険なので、本番運用するなら Route 53 + ACM でALBをHTTPS化するのが最優先の改善点です([インフラ構成図.md](../インフラ構成図.md))。

## 第2章: アプリケーションアーキテクチャ(7問)

### Q9. レイヤードアーキテクチャ

> Controller / Service / Repository の役割を説明してください。
> また、以下も答えてください:
> - なぜ分離するのか
> - ControllerとServiceの責務の境界

**回答:**

#### Controller / Service / Repository の役割

- **Controller(プレゼンテーション層):** HTTPリクエストの受け付け、入力バリデーション、Serviceの呼び出し、HTTPステータスコードやレスポンス(DTO)の返却。
- **Service(ビジネスロジック層):** 業務ルールの適用、トランザクション制御(`@Transactional`)、複数Repositoryの統括・データ整合性の保証。
- **Repository(データアクセス層):** データベースとの通信、SQLの実行、DBレコードとエンティティの相互変換。

#### なぜ分離するのか

各層の関心事を分離(責務の明確化)することで、コードの見通しが良くなり、改修時の影響範囲を局所化できるためです。また、ビジネスロジック(Service)をフレームワークやDB実装から疎結合にすることで、単体テストが容易になります。

#### ControllerとServiceの責務の境界

- 「HTTP通信に関する知識(Cookie、ヘッダー、JSONパース等)」はControllerの責務とし、Serviceには一切持ち込ませません。
- 「業務判断・ドメインロジック(例:投稿文字数の制限チェック、投稿権限チェック、ポイント付与等)」はすべてServiceの責務とします。

### Q10. DTOパターン

> エンティティを直接APIに使わない理由を説明してください。

**回答:**

#### エンティティを直接APIに使わない理由

- **セキュリティ(情報隠蔽):** エンティティのパスワードハッシュ値や内部管理用フラグなど、外部に公開すべきでない情報がレスポンスに漏洩するのを防ぐため。
- **密結合の防止:** DBのテーブル構造(エンティティ)の変更が即座にフロントエンドへのAPI破壊的変更になってしまうのを防ぎ、UIに必要なデータ形状とDBスキーマを独立して進化させるため。
- **過剰なデータ送信の抑制(オーバーフェッチ防止):** 画面表示に不要なカラムを除外し、ネットワーク転送量を最適化するため。

### Q11. グローバル例外ハンドリング

> 各Controllerでtry-catchする場合と比較した利点を説明してください。

**回答:**

#### Controller個別try-catchに対する利点(`@RestControllerAdvice` 等)

- **ボイラープレートコードの削減:** 全Controllerに同じような例外処理やロギングを書く必要がなくなり、コードベースが劇的に簡潔化する。
- **エラーレスポンス形式の全社統一:** 万が一エラーが発生した際、フロントエンドに返却するJSON構造(status, errorCode, message, timestamp等)をシステム全体で一貫させることができる。
- **予期せぬシステム例外の安全な隠蔽:** 想定外のNullPointerException等が発生しても、スタックトレース等の内部情報をクライアントに晒さず、一律で「500 Internal Server Error」として整流して返せる。

### Q12. MyBatis vs JPA

> 以下の観点で違いを説明してください:
> - SQL制御
> - 学習コスト

**回答:**

#### SQL制御

- **MyBatis:** 開発者がXMLやアノテーションに手動で生SQL(または動的SQL)を直接記述します。複雑なチューニング、インデックス最適化、CTE、複数テーブル結合などを100%開発者の意図通りに細かく制御できます。
- **JPA(Hibernate):** ORMがメソッド名やJPQLから自動でSQLを生成します。基本的なCRUDはSQLレスで高速に開発できますが、複雑な検索条件や結合時に意図しない非効率なクエリが発行されやすい傾向があります。

#### 学習コスト

- **MyBatis:** 低い。SQLの読み書きができるエンジニアであれば、マッピングの仕組みを覚えるだけで直感的に習得可能です。
- **JPA:** 高い。エンティティのライフサイクル(永続性コンテキスト)、遅延ロード(Lazy Loading)、キャッシュ機構、N+1問題の回避策などを深く理解していないとパフォーマンス障害を引き起こしやすいです。

> **※このアプリの実際の構成:** このアプリでは Spring Data JPA を採用しています。基本的なCRUDはメソッド名からの自動生成で済ませ、一覧取得のように発行されるSQLを意識すべき箇所は `@Query` でJPQL(フォロー判定の一部はネイティブSQL)を書いて制御しています。

### Q13. 環境ごとの設定管理

> プロファイルの仕組みと、環境ごとに設定を分ける理由を説明してください。

**回答:**

#### プロファイルの仕組み(Spring Profile等)

`application-dev.yml`、`application-prod.yml` のように環境ごとの設定ファイルを分け、起動時引数や環境変数(`SPRING_PROFILES_ACTIVE=prod`)によって読み込む設定を動的に切り替える仕組みです。

#### 環境ごとに設定を分ける理由

開発環境ではローカルDB(H2やDocker MySQL)に接続し、詳細ログ(DEBUG)を出力したいのに対し、本番環境では本番RDSに接続し、セキュリティのため最小限のログ(INFO/ERROR)に絞るなど、インフラ構成・接続先・パフォーマンス・セキュリティの要件が環境ごとに根本から異なるためです。

> **※このアプリの実際の構成:** このアプリでは `application.properties`(共通設定)に加えて、ローカル用の `application-local.properties`(Git管理外)と AWS用の `application-aws.properties` の2つのプロファイルを使い分けています。DBはどちらも PostgreSQL です(ローカルはDockerのPostgreSQL、AWSはRDS)。

### Q14. Flyway(DBマイグレーション)

> マイグレーションツールを使う理由を説明してください。
> (直接ALTER TABLEしない理由)

**回答:**

#### 直接 ALTER TABLE を行わずマイグレーションツールを使う理由

- **スキーマ変更履歴のコード管理(再現性):** `V1__init.sql`, `V2__add_index.sql` のようにバージョン管理され、Gitで変更差分をレビュー可能になります。
- **開発環境・ステージング・本番環境のスキーマ不整合防止:** 各環境へのデプロイ時に未適用のスクリプトが自動実行されるため、「本番環境だけカラム追加を忘れてエラーになる」といった人的ミスを完全に排除できます。
- **自動ロールバック・状態把握:** `flyway_schema_history` テーブルによって、どのマイグレーションがいつ適用されたかを厳密に追跡できます。

> **※このアプリの実際の構成:** このアプリではFlywayはまだ導入しておらず、テーブル定義は `schema.sql` で作成しています。上記の理由から、本番運用でスキーマ変更が発生するようになったらFlywayを導入するのが改善点です。

### Q15. Axiosインターセプター

> インターセプターとは何か説明してください。
> また、これが無い場合の問題点も述べてください。

**回答:**

#### インターセプターとは

HTTPリクエストが送信される前、およびレスポンスが呼び出し元コンポーネントに返却される直前のタイミングに、共通処理を割り込ませて横断的に実行できるミドルウェア機能です。

#### 無い場合の問題点

各API呼び出し関数すべてに、手動で「アクセストークンをヘッダーに付与する処理」や「401 Unauthorizedが発生した際のリフレッシュトークン再取得処理」「共通エラーハンドリング(画面へのトースト通知)」を重複してコピペ記述する必要が生じ、実装漏れや保守性の著しい低下を引き起こします。

> **※このアプリの実際の構成:** このアプリではAxiosは使わず、`fetch` をラップした共通関数([frontend/src/api/http.js](../frontend/src/api/http.js))でインターセプターと同じ役割を実現しています。全APIで「JWTの付与」「エラーの形の統一」「401ならログアウト」をこの1か所で行っています(リフレッシュトークンは無いため、401時はトークン再取得ではなくログアウトします)。

## 第3章: フロントエンド設計(6問)

> **この章について**
> このアプリはAIを活用してフロントエンドを実装しています。

### Q16. React Context

> なぜpropsではなくContextが選ばれたのか説明してください。
> また、適切なケース / 不適切なケースも述べてください。

**回答:**

#### propsバケツリレーではなくContextが選ばれた理由

認証情報(ログイン中ユーザー、トークン)のように、アプリ内のヘッダー、タイムライン、投稿フォーム、サイドバーなど階層の深い複数のコンポーネントで横断的に利用されるグローバル状態を、中間コンポーネントを介さずに直接どこからでも参照できるようにするためです。

#### 適切なケース / 不適切なケース

- **適切なケース:** 更新頻度が低く、アプリ全体で共有されるデータ(ログインユーザー情報、カラーテーマ、UI言語設定など)。
- **不適切なケース:** 更新頻度が極めて高いデータ(テキスト入力フォームの1文字ごとの状態、毎秒更新されるリアルタイムタイマーなど)。Contextが更新されると、そのProvider配下でコンテキストを消費している全コンポーネントが不要に再レンダリングされ、パフォーマンスが著しく劣化するためです。

### Q17. カスタムフック

- **単体テストの容易性:** UIのレンダリングを伴わずに、`renderHook` を用いてロジック部分だけを独立してテストできます。

### Q20. SPAルーティング

> 従来のWebとの違いを説明し、
> 「直接URLで404になる問題」の原因と対策を述べてください。

**回答:**

#### 従来のWebとの違い

- **従来のWeb(MPA):** リンク遷移のたびにブラウザがサーバーへHTMLをまるごとリクエストし、ページ全体を再読み込み・再描画します。
- **SPA(Single Page Application):** 最初の1回だけ共通のindex.htmlとJSを読み込み、ページ遷移時はブラウザのHistory APIを用いてURLのみを書き換え、JavaScriptが差分コンポーネントのみを動的に切り替えます(画面のチラつきがなく爆速)。

#### 「直接URLで404になる問題」の原因と対策

- **原因:** `https://example.com/posts/123` に直接アクセス(またはF5リロード)すると、ブラウザはS3/Webサーバーに対して `/posts/123` という実体ファイルを物理的に探しに行きますが、SPAには `index.html` 以外の物理ファイルが存在しないためWebサーバーが404エラーを返します。
- **対策:** Webサーバー(CloudFrontやNginx)側で、「404エラーが発生した場合はステータスコード200として `/index.html` へフォールバックして転送するルーティング設定」を施します。これにより、クライアント側のReact RouterがURLを解釈して正しい画面を描画します。

> **※このアプリの実際の構成:** このアプリの構成案ではCloudFrontは使わず、EC2上のNginxがReactのビルド済みファイルを配信します。`/users/hanako` のような画面のURLにはNginxが `index.html` を返し、`/api/...` はSpring Bootに転送する設計です([インフラ構成図.md](../インフラ構成図.md))。

### Q21. 楽観的UI更新

> 以下を比較してください:
> - サーバー応答後に更新
> - 楽観的更新
>
> そしてどちらが適切か理由付きで答えてください。

**回答:**

### Q23. AWS基本サービス

> EC2 / RDS / ALB / S3 の役割と分離理由を説明してください。

**回答:**

#### 各サービスの役割

- **EC2(Compute):** サーバー本体。動的なアプリケーション(Java/Spring Boot)を実行する計算資源。
- **RDS(Database):** データベース専用マネージドサービス。自動バックアップ、Multi-AZ冗長化、パッチ当てを代行。
- **ALB(Load Balancer):** アクセス集中時の負荷分散、ヘルスチェックによる障害サーバーの切り離し、SSL暗号化終端。
- **S3(Storage):** 容量無制限の静的オブジェクトストレージ。アイコン画像、アップロード動画、Reactの静的ビルド成果物の配信。

#### 分離する理由(責務分離)

スケーラビリティと耐障害性を独立させるためです。画像配信の負荷でEC2が落ちるのを防ぎ、DB障害時もアプリ層と切り離して復旧できるようにし、各コンポーネントを独立して最適コストでスケールさせます。

### Q26. 構造化ログ

## 第5章: テストと品質保証(5問)

### Q27. テストの種類

> 以下の違いと具体例を説明してください:
> - 単体テスト
> - 結合テスト
> - E2Eテスト

**回答:**

#### 単体テスト(Unit Test)

- **対象:** 関数やクラス、1つのUIコンポーネントなど最小単位の検証。
- **具体例:** 「消費税計算関数に1000を渡すと1100が返るか」「パスワードバリデーション関数が8文字未満を弾くか」。

#### 結合テスト(Integration Test)

- **対象:** 複数のモジュールや、プログラムとDBが組み合わさった連携の検証。
- **具体例:** 「UserControllerの登録エンドポイントを叩いた時、Serviceを経由してテスト用MySQLに正しくINSERTされ、201 Createdが返るか」。

#### E2Eテスト(End-to-End Test)

- **対象:** 実際のブラウザを自動操作し、画面〜サーバー〜DBを通じたシステム全体のユーザーシナリオ検証。
- **具体例:** 「ブラウザで新規登録画面を開き、情報を入力して登録ボタンを押し、タイムライン画面に遷移してウェルカムメッセージが表示されるか」(Playwright等で実行)。

> **※このアプリの実際の構成:** このアプリでは、単体テスト(バックエンドはJUnit、フロントエンドはVitest + React Testing Library)と、Testcontainersで起動したPostgreSQLを使うRepository・APIの結合テストを実装しています。E2Eテストはまだ導入していません。

### Q28. モック(テストダブル)

> モックの利点と注意点を説明してください。

**回答:**

#### モックの利点

- **高速化・安定化:** 外部API通信やDB接続をダミーに差し替えることで、数ミリ秒でテストが完了し、外部要因による不安定さを排除できる。

### Q30. テストカバレッジ

> カバレッジの意味と限界を説明してください。
> 「100%=バグなし」は正しいかも答えてください。

**回答:**

#### カバレッジの意味と限界

- **意味:** ソースコード全体のうち、テストコードを実行した際に通過した行や分岐の割合(網羅率)。
- **限界:** コードの行が実行されたことしか示せず、「仕様の考慮漏れ」「意図しない要件」「非同期の競合状態」「セキュリティの脆弱性」は検知できません。

#### 「100%=バグなし」は正しいか

**誤り(正しくない)**です。極端な例として、アサーション(`expect` による検証)が1行も書かれていないテストであってもコードを通過しさえすればカバレッジは100%になります。また、「仕様書に書かれていない想定外の操作」に対するバグはコード自体が存在しないため、カバレッジでは計測不能です。

### Q31. フロントエンドテスト戦略

**回答:**

#### Testing Libraryの思想

「ユーザーがソフトウェアを利用する方法にテストが似ていれば似ているほど、テストはより信頼できるものになる」
(The more your tests resemble the way your software is used, the more confidence they can give you.)

## 第6章: 設計原則と実務判断(5問)

### Q32. N+1問題

> 概念と、タイムライン例で説明してください。

**回答:**

#### 概念

最初の親レコード一覧を取得するクエリ(1回)を実行した後、関連する子レコードを取得するために親の件数分(N回)の追加クエリがループ等で発行され、DBへのアクセス回数が爆発的に増大してシステムが重くなるパフォーマンス問題です。

#### タイムラインでの具体例

1. タイムラインの投稿20件を取得するクエリ(1回):`SELECT * FROM posts LIMIT 20;`
2. 各投稿に紐づく投稿者情報を取得するためにループ内で20回実行されるクエリ(N回):`SELECT * FROM users WHERE id = ?;`

(計21回発行)

**対策:** MyBatisやSQLで `JOIN` を使って投稿とユーザーを1回のクエリでまとめて取得するか、`WHERE id IN (?, ?, ...)` を用いて一括取得します。

> **※このアプリの実際の構成:** このアプリはMyBatisではなく Spring Data JPA なので、一覧取得ではJPQLの `join fetch` で関連するユーザーを同じクエリで取得し、N+1問題を回避しています(例: コメント一覧・フォロー一覧。[設計書 3-4](../設計書.md#3-4-一覧取得でのn1問題の対策まとめ))。

### Q33. ページネーション

> 必要な理由と、代表的な2方式を比較してください。

**回答:**

#### 必要な理由

数千〜数万件のデータを一度に取得すると、DBのメモリ枯渇、ネットワーク転送遅延、フロントエンドのDOM描画過負荷によりアプリ全体がクラッシュするため、データを一定件数(20件など)ずつ分割取得します。

#### 代表的な2方式の比較

| 比較項目 | オフセットベース(LIMIT / OFFSET) | カーソルベース(Seek法 / `WHERE id < ?`) |
|---|---|---|
| 仕組み | 「先頭からN件読み飛ばしてM件取得」 | 「前回取得した最後のデータIDより後を取得」 |
| 速度 | データが深くなる(ページが進む)ほど激遅 | インデックスを効かせるため何億件あっても爆速 |
| ズレ問題 | 取得中に新着投稿があると重複や表示ズレが発生 | 取得中に新着が入っても絶対にズレない |
| 適した用途 | 管理画面、通常の「1, 2, 3ページ」ボタン | SNSのタイムライン、無限スクロール |

### Q34. 画像アップロード設計

> DB保存とS3保存の違いと利点を説明してください。

**回答:**

#### DB保存(BLOB)とS3保存の違い

- **DB保存(BLOB):** 画像バイナリを直接テーブルのカラム(LONGBLOBなど)に格納する。
- **S3保存:** 画像ファイル本体はS3バケットにアップロードし、データベースにはそのS3のアクセスURL(文字列)のみを保存する。

#### S3保存の利点

- **DBの負荷・容量の劇的削減:** 巨大なバイナリを扱わないため、DBのメモリ効率が向上しバックアップやリストアが一瞬で完了する。
- **コストの圧倒的削減:** 高価なRDSストレージを消費せず、GBあたり月額数円の安価なS3に退避できる。
- **配信パフォーマンスの向上:** S3の手前にCloudFront(CDN)を配置することで、画像配信をエッジサーバーから世界中へ爆速でキャッシュ配信できる。

#### 代表的な方式と特徴

1. **URIパスマッピング方式(業界デファクト)**
   - 例:`/api/v1/posts`, `/api/v2/posts`
   - 特徴:URLを見ればどのバージョンか一目で分かり、CDNのキャッシュ制御やルーティングが最も容易。
2. **カスタムリクエストヘッダー方式**
   - 例:`X-API-Version: 2`
   - 特徴:リソースのURIが変わらないRESTfulな美しさがあるが、ブラウザのアドレスバーから直接叩きにくく、テストやCDN設定がやや煩雑になる。
3. **Acceptヘッダー(Content Negotiation)方式**
   - 例:`Accept: application/vnd.company.v2+json`
   - 特徴:REST原則に最も忠実だが、クライアント側の実装難易度が高く可読性が低い。

### Q36. 技術選定

> 判断基準を説明し、
> React + Spring Boot + PostgreSQL を例に具体化してください。

**回答:**

#### 技術選定の判断基準

- **要件適合性:** そのアプリの目的(リアルタイム性、SEO、拡張性など)を最もシンプルに満たせるか。
- **開発速度と保守性:** エコシステムやライブラリが成熟しており、長期的なメンテナンスが可能か。
- **チームの習熟度と採用容易性:** 市場にエンジニアが多く存在し、ドキュメントが豊富でトラブル時に解決しやすいか。

#### 「React + Spring Boot + PostgreSQL」選定の具体化理由

- **フロントエンド(React + TypeScript):** SNS特有のリッチなUIインタラクション(いいねアニメーション、リアルタイム更新、無限スクロール)を、成熟したコンポーネント指向と広大なエコシステムで高速に構築できる。
- **バックエンド(Spring Boot / Java):** 堅牢な型システム、強力な依存性の注入(DI)、充実したセキュリティ機構(Spring Security)により、大規模化しても保守性が崩れない強固なエンタープライズ品質のAPIサーバーを構築できる。
- **データベース(PostgreSQL):** SNSのデータ構造(ユーザー、フォロー、投稿、いいね)は典型的なリレーショナル関係であり、ACIDトランザクションの完全な保証が必要。また、JSON型や全文検索にも対応しており、将来の機能拡張にも柔軟に対応できる実績抜群のRDBMSであるため。

> **※このアプリの実際の構成:** このアプリのフロントエンドはTypeScriptではなくJavaScript(React + Vite)で実装しており、API の型だけを OpenAPI 仕様書から `schema.d.ts` として自動生成しています(Q19の補足を参照)。
